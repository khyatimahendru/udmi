# UDMI Discovery Messages Guide & Captured Examples

This directory contains real discovery message captures generated by running the **UDMI Spotter** agent and the **Legacy Discovery Node** against a simulated multi-device BACnet testbed and local MQTT broker, captured using UDMI canonical pipeline tooling (`bin/pull_save` and `bin/pull_messages`).

---

## 1. Executive Summary & Batch Lifecycle Architecture

In UDMI, discovery and site-model batching rely on two core fields:
1. **`generation`**: An RFC 3339 UTC timestamp (`YYYY-MM-DDTHH:MM:SSZ`) identifying the unique commit/scan batch. The `generation` timestamp is strictly identical across all messages in that batch and monotonically increases for subsequent batches.
2. **`event_no`**: An integer sequence identifying each message's position and bounding the batch:
   - **START Marker**: `event_no == 0` (marks batch start; unpopulated fields omitted)
   - **Device Events**: `event_no == 1, 2, ... N` (where $N$ is the number of discovered entities)
   - **STOP Marker**: `event_no == -(N + 1)` (marks batch completion; $N = |event\_no| - 1$ total devices)

### Sequence Example ($N = 2$ devices)
```text
  Message 1: event_no =  0  (START Marker: indicates batch start for generation G)
  Message 2: event_no =  1  (Device 12341 discovered)
  Message 3: event_no =  2  (Device 12342 discovered)
  Message 4: event_no = -3  (STOP Marker: denotes completion; N = |-3| - 1 = 2 devices)
```

## 3. Message Structure Breakdown

### A. START Marker (`event_no: 0`)
The START marker is published when the scan or batch ingestion begins. It establishes the active `generation` ID and protocol/family without device-specific fields (unpopulated fields like `addr`, `system`, etc., are omitted per UDMI non-null sparse specification).

#### Envelope (`.attr`):
```json
{
  "deviceId": "DSN-1",
  "deviceRegistryId": "ZZ-TRI-FECTA",
  "subFolder": "discovery",
  "subType": "events",
  "publishTime": "2026-09-24T09:19:09Z",
  "projectId": "my-project",
  "topic": "/r/ZZ-TRI-FECTA/d/DSN-1/events/discovery"
}
```

#### Payload (`.json`):
```json
{
  "timestamp": "2026-09-24T09:19:09.545953+00:00",
  "version": "1.5.7",
  "generation": "2026-09-24T09:19:07Z",
  "family": "bacnet",
  "event_no": 0
}
```

---

### B. Discovered Device Message (`event_no: 1, 2, ... N`)

### D. STOP Marker (`event_no: -(N + 1)`)
The STOP marker signals the scan is finished. Like the START marker, it contains no device address, but its `event_no` carries the negative device count bounding the batch:

#### Payload (`.json`):
```json
{
  "timestamp": "2026-09-24T09:19:19.666201+00:00",
  "version": "1.5.7",
  "generation": "2026-09-24T09:19:07Z",
  "family": "bacnet",
  "event_no": -3
}
```
*Note*: For $N = 2$ devices (`12341` and `12342`), the stop marker event number is $-(2 + 1) = -3$.

## 4. Downstream Ingestion Pipeline Pattern

1. **Interleaving Resolution**:
   - Incoming messages are keyed and staged into raw storage partitioned by `generation`.
   - If messages from generation $T_1$ and $T_2$ arrive out of order, they isolate into separate generation buckets. Older generations can be safely discarded once a newer generation completes.

2. **Validation Trigger & Device Count Verification**:
   - When the STOP event arrives with `event_no == -M`, the consumer determines expected count $N = |M| - 1$.
   - The consumer queries `COUNT(DISTINCT addr)` for that `generation`.
   - If `COUNT == N`, all device messages for that batch are present, triggering immediate validation.
   - If `COUNT < N`, the consumer holds the batch and waits for lagging messages up to a configured timeout (e.g. 60–90 seconds).

3. **Atomic Commit & Pruning (Deletions)**:
   - When validation passes, the batch is committed to the target model storage.
   - Any device previously stored that was **not** present in the latest successfully validated generation is considered deleted/retired and can be safely pruned or marked inactive.
